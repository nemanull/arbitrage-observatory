# Exchange Reference Data Seed Design

**Status:** Done.

**Archived:** 2026-07-28.

## Purpose

The schema in [`schema.prisma`](../../server/prisma/schema.prisma) defines `Exchange`, `ExchangeConfig`, and `ExchangeFee` but no rows exist yet.
This design records how those rows reach every database, and where their values come from.

The work covers Binance, Bybit, OKX, Coinbase, and Kraken spot markets.
It does not add adapters, connections, or market discovery.

## Scope

In scope is one `Exchange` row, one `ExchangeConfig` row, and one or more `ExchangeFee` rows per exchange.
Out of scope are `Pair`, `Market`, and `ArbitrageOpportunity`, which are written by the market sync job and the detector rather than by hand.

## Where the values come from

Every value traces to the profiles under [`profiles/`](../profiles/), which are the source of record.
No value is taken from memory of an exchange API, and no value is invented to fill a column.

`ExchangeConfig` values fall into two kinds.
Published constants such as the endpoint URL, the stream limit, and the connection lifetime are copied from the profile.
Engineering choices such as `subscribeIntervalMs` and `reconnectMinDelayMs` are derived from a documented rate limit with headroom left over, and the derivation is recorded in [`2026-07-28-exchange-seed-plan.md`](./2026-07-28-exchange-seed-plan.md).

`ExchangeFee` values are the published spot rates for a new account.
That means no volume tier, no token discount, and no promotional programme.

## Decisions

1. Reference data ships inside a migration, not a seed script.
   A migration runs exactly once per database and is recorded in `_prisma_migrations`, so every environment converges without an extra command that somebody can forget.
2. Schema and data live in separate migrations.
   `20260729044018_init` creates the tables.
   A second migration inserts the reference rows.
   Keeping them apart means a later schema change regenerates cleanly without touching seeded data.
3. Seeded fees are the entry tier rather than a tier we might qualify for later.
   The entry tier is the most expensive one, so the detector understates the edge.
   A system that reports a spread it cannot actually capture is worse than one that misses a marginal spread.
4. A fee class exists only when the venue publishes a different spot rate for a group of markets.
   `Market.feeClass` points at these keys, so a class that does not exist here cannot be assigned there.
   Every exchange has a `default` class.
5. `effectiveFrom` is the retrieval date of the profile that supplied the rate, not the time the migration ran.
   The column answers when the rate was true, and the migration timestamp already answers when the row was written.
6. The seed migration resolves foreign keys by subselecting on `Exchange.slug` rather than writing literal ids.
   Autoincrement ids are only predictable on a database that has never seen a failed insert.
7. `Exchange.slug` must equal the adapter key used in code, which the schema already requires.
   The slugs are `binance`, `bybit`, `okx`, `coinbase`, and `kraken`.
8. One `Exchange` row means one venue, and where a brand runs several venues the seeded endpoint and the seeded fee must describe the same one.
   Coinbase is the only brand here that does.
   Advanced Trade was chosen for both, because it is the platform whose spot book is public without authentication.

## Rejected alternatives

### A `prisma/seed.ts` script

This is the Prisma default and it is easy to edit.
It was rejected because seeding then becomes a separate step outside migration history.
A database can be fully migrated and still be empty, which is a failure mode that only shows up at runtime.

### Seeding every published VIP tier

This would let the detector model a future account level.
It was rejected because we trade at one level, and the extra rows would need a tier resolution rule that nothing needs yet.
`ExchangeFee` is append only, so tiers can be added later without a schema change.

### One migration for schema and data

This would be one file instead of two.
It was rejected because it couples an unstable artefact to a stable one.
Schema changes are regenerated by Prisma, and hand-written data in the same file would be lost or duplicated.

### Hardcoded exchange ids in the fee and config inserts

This would be shorter to write.
It was rejected because it silently binds correctness to insert order.

## Verification

The migration is applied to a fresh database from an empty state, not only to the current one.
Row counts are checked per table.
Every `ExchangeConfig` row is checked against its profile citation.
Every `ExchangeFee` ppm value is recomputed from the percent the profile prints.
`prisma migrate dev` reports no drift and no pending schema change afterwards.

## Reconciliation

The delivered work matches this design.
Five exchanges, five configs, and fifteen fee classes were seeded by `20260729045500_seed_exchanges`, which runs after the schema migration `20260729044018_init`.

Decision 8 was added during execution.
The design originally treated an exchange as a single venue, which does not hold for Coinbase.

Two values could not be sourced the way the design assumed.
Coinbase publishes no subscription count for Advanced Trade, so that number is an engineering cap rather than a published constant.
Bybit publishes no inbound message rate for its public feed, so its subscribe interval is a plain default rather than a derived one.
Both are marked as such in [`2026-07-28-exchange-seed-plan.md`](./2026-07-28-exchange-seed-plan.md) and in the migration comments.

Fee class membership stayed unresolved, which the design anticipated but did not state.
Eight of the fifteen classes exist without a published pair list, so every market starts on `default` until live venue data can assign it.
