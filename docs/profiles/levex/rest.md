# LeveX REST Profile

**Status:** Done.

**Retrieved:** 2026-09-22.

**Probed:** 2026-09-22 local time, 03:13 to 03:39 UTC on 2026-09-23, from the development host near Seattle.

LeveX publishes no REST API.
Its help center says "We don't currently offer an API, but it's something we're exploring for the future.", last updated 2025-04-30, S1.
No documentation host was found, and CCXT has no LeveX class, see [`fees.md`](./fees.md) section 8.
This profile records what was checked instead: the REST host that LeveX's own web page calls, which refused this machine on every path, and the all market ticker on the web client's socket, which is the only place index, mark and funding were readable.
Every probe number is from [`rest-probe.mjs`](../../../scripts/probes/venues/levex/rest-probe.mjs) or [`ws-probe.mjs`](../../../scripts/probes/venues/levex/ws-probe.mjs).

## 2. Catalog

### The instruments call

The web client loads its catalog from `/public/pairs`, with `/public/pairs/md5-version` to check for changes and `/public/pairs/currencies` beside it, S2.
All three sit on `api100.levex.com`, and `/public/pairs` answered 403 on every attempt, so no catalog field was read.
The catalog carries at least `symbol`, `urlSymbol`, `pairName`, `pricePrecision`, `sizePrecision`, `contractSize`, `status`, `contractSide`, `marginType`, `baseCurrency`, `quoteCurrency`, `settleCurrency`, `underlyingAssets`, `fundingInterval`, `fundingCap` and `fundingFloor`, since the web client reads those names from it, S2.
Their values and the list of `status` values are Not verified.

### What the socket lists instead

The all market ticker on the socket, `perp24HTicker.subscribe`, returned 332 rows in each of four runs, P2.

| family | spelling | listed | mark above 0 |
|---|---|---|---|
| USDT-M | `BTCUSDT` | 298 | 254 |
| USDC-M | `BTCUSDC` | 22 | 22 |
| coin-M | `cBTCUSD` | 12 | 10 |

The 286 contracts with a mark above 0 match CoinGecko's 286 perpetual pairs and its split of 254 USDT, 22 USDC and 10 USD, S3.
The 46 others have a mark, bid and ask of 0, 43 of them an index of 0 as well, and an empty book, and several have delisting posts, see [`fees.md`](./fees.md) section 3.
Among the USDT-M contracts are stock, ETF and commodity perpetuals such as `XAUUSDT`, `CLUSDT`, `KOUSDT`, `NETUSDT`, `SHOPUSDT`, `RDDTUSDT`, `EWYUSDT` and `SOXLUSDT`.

### How CCXT maps it

CCXT has no LeveX class, so there is no `market.id`, `contractSize`, `linear` or `active` to compare.
The socket symbol equals the last path segment of CoinGecko's `trade_url`, `https://levex.com/en/perp/trade/0GUSDT` for `0G-PERP_USDT`, S3.

### Size unit, pairs listed twice, and price scale

`contractSize` is in the refused catalog.
The ticker's turnover over volume times last price was 0.93 at the 5th percentile, 0.98 at the median and 1.01 at the 95th over 275 linear contracts with volume in each of runs 2 to 4, P2, so linear volume counts base units.
Coin-M volume counts US dollars: `cBTCUSD` showed a volume of 2,329,331 against a turnover of 27.10 BTC.
Whether book sizes use the same unit as ticker volume is an inference, see [`websocket.md`](./websocket.md) section 4.

BTC, ETH, SOL, XRP, DOGE, BNB, BCH and LINK each trade on an active USDT, USDC and coin-M contract, P2, so one pair appears up to three times, and the engine's `marketFilter` would have to pick one.
Symbols with a multiplier in the name, such as `1000PEPEUSDT` and `1000000BABYDOGEUSDT`, need the same price scale as on other venues.
Equity tickers such as `NET`, `SHOP` and `KO` could name a different token on another venue, which is what a `DENIED_PAIRS` line is for.

## 3. Anchor

### The bulk calls

No REST call was reachable.
The web client's only public REST funding call, `/service-perpetual/trading/public/funding-rate`, is a history call and answered 403, S2 and P1.

The socket's `perp24HTicker` stream is the only bulk source seen, P2.

| item | value |
|---|---|
| subscribe | `{"method":"perp24HTicker.subscribe","params":{},"id":2}` |
| first frame | a snapshot of 332 rows, 45 KB, with a `keys` array naming 14 columns |
| later frames | incremental, one every 1,000 ms median and at most 1,027 to 1,100 ms apart, carrying only the 95 to 223 rows that changed, about 20 KB |
| columns | `symbol`, `lastPrice`, `bidPrice`, `askPrice`, `openPrice`, `highPrice`, `lowPrice`, `indexPrice`, `markPrice`, `fundingRate`, `lastFundingRate`, `volume`, `turnover`, `openInterest` |
| source time | none, so a reading can only be stamped on arrival |

### Row mapping

| `AnchorRow` column | field | unit on the wire | conversion |
|---|---|---|---|
| key | `symbol` | string, `BTCUSDT` | none |
| `index` | `indexPrice` | decimal string, `"0"` on inactive rows | `Number()` |
| `mark` | `markPrice` | decimal string, `"0"` on 46 inactive rows | `Number()` |
| `fundingRate` | `fundingRate` | decimal string, a fraction: `"0.0001"` is 0.01 % | `Number()` |
| `fundingIntervalHours` | none on the socket | `fundingInterval` in seconds in the refused catalog | 8, from the help center, S4, for every contract until the catalog is readable |
| `nextFundingAt` | none on the socket | | the next of 00:00, 08:00 and 16:00 UTC, S4, which matches the web client's countdown `interval - now mod interval`, S2 |

`lastFundingRate` is the rate settled at the last timestamp and `fundingRate` the rate for the next one, since `BTCUSDT` read `-0.000262` and `-0.000214` side by side at the end of run 4, and `fundingRate` changed within a run while `lastFundingRate` never did, section 4.
That reading is an inference from field names and one change.

## 4. Anchor semantics

### Index

The index formula and basket are Not publicly specified.
The sitemap lists `/en/perp/usd-m/index` and `/en/perp/coin-m/index`, and the USDT-M page answered 404, S5.
USDT-M and USDC-M contracts on the same coin carry different index prices, `86750.7` for `BTCUSDT` against `86741.6` for `BTCUSDC` at the end of run 4, so each is priced in its own quote, P2.

### Mark

The mark formula and its clamps are Not publicly specified.
Over the 286 active rows of the ticker snapshot, P2:

| test | runs 2 and 3 | run 4 |
|---|---:|---:|
| mark equals last | 20, 20 | 17 |
| mark equals the median of bid, ask and last | 25, 18 | 19 |
| mark inside the bid and ask | 107, 90 | 113 |
| mark within 20 ppm of index times one plus the funding rate times the share of 8 h left to the next settlement | | 64 |
| mark between that value and last | | 142 |

So the mark is not the book, and it leans on the index when the book moves away.
`MTLUSDT` showed it in run 4: bid `0.31206`, ask `0.31207`, index `0.32313`, funding `-0.003057`, and mark `0.3226`, 3.4 % above the book.
The index times one plus the rate times the 0.5459 of the interval left is 0.32259, which rounds to that mark.
Mark over index was -62 to +4 ppm at the 5th percentile, +95 to +97 at the median and +294 to +361 at the 95th over runs 2 to 4, with minima of -4,220 and -1,640 and maxima of +824 to +916, P2.

### Funding

"the price difference between the perpetual contract price and the spot price, combined with an interest rate component", with no equation, S4.
The web client reads a `fundingCap` and a `fundingFloor` per contract from the refused catalog, so the rate is presumably clamped, and the values are Not verified.
282 of 286 active contracts read exactly `0.0001` or `0.00005` in every run, see [`fees.md`](./fees.md) section 6.

### Rate across a settlement

No settlement instant was captured.
The history call answered 403, so settled rates could not be read either.

### How often each number changed

| contract | rows received | index changed | mark changed | funding changed | last funding changed | last changed |
|---|---:|---:|---:|---:|---:|---:|
| `BTCUSDT` | 61 | 53 | 43 | 0 | 0 | 40 |
| `BTCUSDC` | 58 | 48 | 49 | 1 | 0 | 22 |
| `ETHUSDT` | 55 | 43 | 26 | 0 | 0 | 29 |
| `XAUUSDT` | 41 | 18 | 27 | 0 | 0 | 9 |
| `STORJUSDT`, inactive | 2 | 0 | 0 | 0 | 0 | 0 |

In run 2 the `BTCUSDT` index changed on 30 of 58 rows, so a busy index moves every one or two seconds.

## 7. Server time and clock offset

No server time call is reachable.
The HTTP `Date` header of every reply was within 1 s of this host's clock, which is the header's resolution, P1.
Book frames carry a nanosecond `timestamp`, and arrival minus that timestamp was 50 to 57 ms at the minimum over runs 2 to 4 against a ping round trip near 95 ms, so the offset is a few tens of milliseconds at most, see [`websocket.md`](./websocket.md) section 5.

## 8. Recommended poller shape

No poller is recommended.
[`AnchorPoller.ts`](https://github.com/nemanull/arbitrage-observatory/blob/2cbe70629c3c429da9b231ab71a7b861b3fc8096/server/src/feeds/anchor/AnchorPoller.ts) fetches a JSON reply over HTTP at line 224, and LeveX answers no public REST call from this host.
The only bulk anchor source is a socket stream that LeveX does not publish as an API, and both LeveX agreements forbid scripts that monitor the site, see [`fees.md`](./fees.md) section 1.

If LeveX ever publishes an API, the probe suggests:

| item | suggestion | reason |
|---|---|---|
| source | the all market ticker, `perp24HTicker`, held open on one socket | one frame a second carries index, mark and funding for every contract |
| row mapping | section 3, key `symbol` | |
| interval and next settlement | from the catalog's `fundingInterval`, else 8 h at 00:00, 08:00 and 16:00 UTC | the ticker has neither |
| skip | rows whose `markPrice` is `"0"` | 46 inactive rows |
| receive time | stamp on arrival | the ticker has no source time |
| mark caveat | the mark leans on index plus funding and can sit far from a LeveX book that has left the index | `MTLUSDT` in section 4, 3.4 % between mark and book |
