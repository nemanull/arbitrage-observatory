# HTX WebSocket Profile

**Status:** Done.

**Retrieved:** 2026-09-22.

**Probed:** 2026-09-22 local time, from the development host near Seattle, 03:08 to 03:46 UTC on 2026-09-23.

This profile covers the public futures WebSocket of HTX (CCXT id `htx`) for the USDT-margined perpetuals in detail and the coin-margined perpetuals where they differ, with the book channel in detail.
Every protocol claim below was captured by [`ws-probe.mjs`](../../../scripts/probes/venues/htx/ws-probe.mjs), in two runs about thirteen minutes apart, and a pair such as "388 and 379 ms" gives the first run and then the second.
Where the documentation and the wire disagree, both are written, and the wire is what a feed must handle.
The documentation of record is the USDT-M reference at `huobiapi.github.io`, S1, and HTX's 2026 V5 migration left market data interfaces unchanged, see [`rest.md`](./rest.md) introduction.

Every frame the server sends is a binary frame holding a gzip member, and the engine's feeds decode text JSON today, see section 5.

## 4. The book channel in detail

`market.<code>.depth.size_20.high_freq` with `data_type` `incremental` is the channel this profile recommends, and every row below is about it unless it says otherwise.

### Snapshot on subscribe

The first frame of each stream is `"event": "snapshot"` with 20 bids and 20 asks, or 150 and 150 on `size_150`, and its `version`.
Six streams in each run got their snapshot 279 to 292 ms after the subscribe frame was sent, each right after its acknowledgement.
The snapshot's `ts` is the time of the book's last change, so it can be older than the acknowledgement: `STEEM-USDT` read 630 ms older in the second run.
S1 says "when data_type is incremental,snapshot data wil be pushed for the first time. When re-connection occurs, snapshort data will be pushed for the first time."
A second subscribe to the same topic, in the same case or in lower case, was acked `ok` and sent a fresh snapshot, whose `version` continued the chain, so `BTC-USDT` got 3 snapshots in each run and no gap.
A second subscribe without `data_type` is acked `ok` and adds full `snapshot` frames on the same `ch`, interleaved with the incremental ones, which is why `ETH-USDT` shows 755 and 1,963 snapshots.

### Delta semantics

A delta is `"event": "update"` with `bids` and `asks` arrays of `[price, size]` number pairs, and a size of 0 deletes the level.
A delta with both arrays empty is legal and only advances `version`: 9 of 735 and 15 of 1,708 `BTC-USDT` deltas, and 301 of 28,496 and 455 of 34,176 in the 150 stream runs.
S1 adds "you HAVE TO maintain local orderbook data".

### Sequence and gap rule

```text
event = snapshot                 replace the book, last = version
event = update, version = last+1 apply, last = version
event = update, otherwise        gap: resubscribe or reconnect, which is the engine's resync
```

CCXT Pro applies the same rule, `version - 1 === orderbook['nonce']`, at `server/node_modules/ccxt/js/src/pro/htx.js` line 712.
The rule held on every delta of both runs, with 0 gaps: 4,797 and 7,936 deltas on six streams in `book`, and 28,496 and 34,176 on 150 streams in `batch`.
`version` values are large per stream counters, such as 1789895280797 for `BTC-USDT` and 1789892505763 for `STEEM-USDT`, and S1 says they may differ between connections, so a feed never compares them across sockets.

### Checksum

None is documented for the contract depth channels, and no frame carries one.
CCXT Pro's `checksum` option at `pro/htx.js` line 112 guards the spot `seqNum` chain, not this one.

### Level order on the wire

| frame | bids | asks |
|---|---|---|
| snapshot | descending on every snapshot of both runs | ascending |
| delta | descending on every delta with more than one bid, 0 exceptions | ascending, 0 exceptions |
| REST `market/depth` | descending | ascending |

The order held on every frame, and a feed still applies deltas by price.

### Level window

The server keeps the stream at 20 levels per side, or 150.
A book maintained from the snapshot and every delta never held more than 20 levels on any of the 150 streams, and a level leaving the window arrives with size 0, as the `STEEM-USDT` delta in section 6 shows.
The engine holds 20 levels per side by default, at [`../../../server/src/engine/Engine.ts`](../../../server/src/engine/Engine.ts) line 61, so `size_20` covers it and `size_150` leaves room.

### Size unit against CCXT `contractSize`

| contract | CCXT `contractSize` | socket size at the touch, first run | coins |
|---|---:|---|---|
| `BTC-USDT` | 0.001 | `229` | 0.229 BTC |
| `ETH-USDT` | 0.01 | `6068` | 60.68 ETH |
| `STEEM-USDT` | 1 | `307` | 307 STEEM |

The unit is contracts, and one contract is `contract_size` coins, which is exactly CCXT's `contractSize`, see [`rest.md`](./rest.md) section 2.
After 20 s of deltas, the maintained top 10 per side matched the REST `step0` book at the same price on 16, 18 and 20 of 20 levels for BTC, ETH and STEEM in the first run and 17, 15 and 17 in the second, and every mismatch was a size that moved between the two reads.

### One-sided and empty books

No one-sided book was seen.
A suspended contract, `CYBER-USDT` with `contract_status` 3, was acked `ok` and sent no snapshot and no delta in 75 s in either run, and its REST book is empty.
The engine's `resetBook` accepts an empty side.

### Idle repeats

Nothing is repeated, and a quiet stream sends nothing.
`STEEM-USDT` went 1,843 and 1,957 ms and `XAU-USDT` 2,731 and 2,399 ms without a frame in the 75 s runs.
Across the 150 streams, the longest gap per stream had a median of 2,503 and 2,583 ms, a p90 of 11,084 and 10,887 ms, and a maximum of 24,128 and 28,637 ms.

### Unknown, closed and wrong-level symbols

| request | reply | then |
|---|---|---|
| `market.NOPE-USDT.depth.size_20.high_freq` | `"err-code":"bad-request","err-msg":"invalid topic market.NOPE-USDT.depth.size_20.high_freq"` | nothing |
| `size_30`, `size_5` or `size_400` | `invalid topic`, although CCXT Pro allows 5, 20, 150 and 400 at `pro/htx.js` line 437 | nothing |
| `market.CYBER-USDT.depth.size_20.high_freq`, suspended | `"status":"ok"` | nothing in 75 s |
| the same topic twice | `"status":"ok"` | a fresh snapshot, the chain continues |
| `market.BTC-USD.depth.size_20.high_freq` on the USDT-M URL | `invalid topic` | nothing |
| `market.BTC-USDT.nope` | `invalid topic market.BTC-USDT.nope` | nothing |
| text that is not JSON | `"err-code":"bad-request","err-msg":"not json, is not json string"` with an empty `id` | the socket stays open |

Because a suspended contract is acknowledged and never served, the feed has to notice a stream with no snapshot on its own.

## 5. Session

| item | documented, S1 | probed |
|---|---|---|
| framing | "All response data from WebSocket server are compressed into GZIP format. Clients have to decompress them for further use." | every frame of every socket was binary gzip, 18,186 of 18,186 on the second `book` socket and 34,489 of 34,489 on the second `batch` socket. Decompressed text was 1.6 to 1.84 times the compressed size |
| decode cost | | `gunzipSync` per frame on this laptop: median 41 and 26 µs on `book`, 24 and 18 µs on `batch`, p90 50 to 81 µs. `JSON.parse` after it: median 6 to 10 µs. So the gunzip is about three times the parse |
| keepalive | server `{"ping": <ms>}` every 5 s, client answers `{"pong": <ms>}`. The notification URL uses `{"op": "ping", "ts": "<ms>"}` and expects `{"op": "pong", "ts": "<ms>"}` | market sockets: ping every 4,805 to 5,176 ms. Notification socket: 5,274 to 5,376 ms. A client `{"ping": <ms>}` was never answered |
| silence the server tolerates | "The connection will get disconnected automatically if the WebSocket Client ignores the heartbeat message for 5 times" | a socket that does not answer pings closed with 1003 `ping check expired` at 20,044, 20,428, 20,119 and 21,060 ms, after 4 unanswered pings, whether or not it had a subscription. A socket that answers pings stayed open for the full 120 s with no subscription |
| forced disconnect | Not publicly specified | none in 120 s |
| maintenance notice | `public.$service.heartbeat` on `center-notification`, and REST `/heartbeat/` | not observed |
| compression negotiation | | a client that offered permessage-deflate got no `sec-websocket-extensions` header back, and the frames stayed gzip, 17 and 96 of 17 and 96 binary |
| handshake | | 379 to 900 ms to open over all runs |
| subscription limits | 40 subscriptions per second, and "the WS request connection should not go over 30 normally" in the order push section | 60 in one burst accepted. 150 streams on one socket ran with 0 gaps |
| throughput | | 150 USDT-M perpetuals, every other one by 24 h turnover: median 457 and 535 frames per second, peak 634 and 977, about 93 and 111 KB per second compressed, about 205 bytes compressed and 330 bytes decompressed per frame |

The engine refuses permessage-deflate at [`../../../server/src/feeds/book/VenueFeed.ts`](../../../server/src/feeds/book/VenueFeed.ts) line 81, and that does not matter here, because the gzip is inside the frame.
`VenueFeed` hands `handleMessage` the raw `Buffer`, at line 209, so a subclass can gunzip it before parsing, and no feed in the engine does so today.
At the second `batch` rate, 535 frames per 150 streams per second at 18 µs, the gunzip adds about 10 ms of loop time per second per 150 streams, on top of the parse.

## 7. Private channels

Named for a future execution stage, from S1 and CCXT Pro, not probed.

- The V1 order push URL is `wss://api.hbdm.com/linear-swap-notification`, with a login frame `{"op": "auth", "type": "api", …}` and topics such as `orders_cross.$contract_code`, `positions_cross.$contract_code`, `accounts_cross.$margin_account`, `matchOrders_cross.$contract_code` and `trigger_order_cross.$contract_code`.
- CCXT Pro also lists a V5 private URL, `wss://api.hbdm.vn/ws/v5/notification`, at `pro/htx.js` line 54.
- HTX required API users to move USDT-M order, account and position calls to V5 by 2026-09-19 16:00 UTC, so a future execution stage starts from the V5 documentation, see [`rest.md`](./rest.md) introduction.

## 8. Recommended feed shape

A recommendation for a later design, not a decision.

| item | recommendation | reason |
|---|---|---|
| URL plan | one plan for USDT-M, `wss://api.hbdm.vn/linear-swap-ws` | one family per socket, and the coin-M contracts are best filtered out, see [`rest.md`](./rest.md) section 2 |
| channel | `market.<rawMarketId>.depth.size_20.high_freq` with `data_type` `incremental` | snapshot on subscribe, a strict per stream `version` chain, 20 levels matches the engine |
| markets per connection | 150 | 150 streams ran with 0 gaps at up to 977 frames per second, and no per socket cap is published, so a larger slice is untested |
| subscribe frames | one frame per market, `{"sub": "market.BTC-USDT.depth.size_20.high_freq", "data_type": "incremental", "id": "<n>"}`, at most 40 per second | the documented pace, and a topic cannot be batched |
| decode | `JSON.parse(gunzipSync(raw))` in `handleMessage` | every frame is gzip, section 5 |
| keepalive | answer each `{"ping": n}` with `{"pong": n}` from `handleMessage`, and let `startKeepalive` send nothing | the server pings every 5 s and closes at about 20 s without an answer, and a client ping is not answered |
| `maxSilenceMs` | 15,000 | three missed server pings, and the pings count as traffic, since a quiet stream went 28.6 s without a book frame |
| routing | `ch.split('.')[1]` gives the `rawMarketId` | the channel wraps the code, always upper case |
| snapshot | `event === 'snapshot'`: `resetBook`, store `version` | documented replace semantics, and a resubscribe sends one |
| delta | apply only when `version === last + 1`, then store `version`, including for empty deltas | 0 gaps observed |
| resync | a `version` that is not `last + 1`, or a delta before any snapshot: `resync` | the engine's existing path, and a reconnect brings a snapshot |
| unserved stream | log a stream with no snapshot 10 s after its ack | a suspended contract is acked and silent |
| one subscription per topic | never subscribe a topic twice, and never without `data_type` | a second plain subscribe interleaves full snapshots on the same `ch` |
| receive time | stamp on arrival, never from `ts` | the engine's rule, and `tick.ts` is about 140 to 160 ms old here |
| sizes | the number as sent, times `contractSize` | contracts, section 4 |
| deflate | keep `perMessageDeflate: false` | the server does not negotiate it, and the gzip is inside the frame |
